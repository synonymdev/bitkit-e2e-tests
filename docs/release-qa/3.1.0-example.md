## Selected sanity cases

Each case has status **Not run**; tester/date, device/OS, actual build and execution evidence are **not yet recorded**. Populate those fields independently per platform when running the plan. Payment/proof references belong in the execution record with appropriate privacy controls.

### MN-BTC-A — Bitcoin mainnet

- **Scope:** Recurring · Android.
- **Steps and pass condition:** Send and receive a small amount, including an external wallet. Confirm recipient output, amount and fee independently. After confirmation/reopening, balances and activity reconcile with no duplicates.
- **Why selected:** Production binary/services check; do not repeat address-type, coin-selection or Boost matrices.
- **Status:** Not run.

### MN-BTC-I — Bitcoin mainnet

- **Scope:** Recurring · iOS.
- **Steps and pass condition:** Send and receive a small amount, including an external wallet. Confirm recipient output, amount and fee independently. After confirmation/reopening, balances and activity reconcile with no duplicates.
- **Why selected:** Production binary/services check; existing E2E covers functional variations.
- **Status:** Not run.

### MN-LN-A — Lightning / Paykit request

- **Scope:** Recurring + 3.1.0 · Android.
- **Steps and pass condition:** Send/receive via BOLT11 and make one external Lightning-address payment. Use a fixed Paykit request offering Savings and Spending for one outgoing payment: switch source, retain requested value, show the appropriate fee, authorize once and verify recipient settlement and requester proof.
- **Why selected:** Recurring production route smoke; source-selection variant closes a 3.1.0 live Lightning gap. https://github.com/synonymdev/bitkit-android/pull/1713
- **Status:** Not run.

### MN-LN-I — Lightning / Paykit request

- **Scope:** Recurring + 3.1.0 · iOS.
- **Steps and pass condition:** Send/receive via BOLT11 and make one external Lightning-address payment. Use a fixed Paykit request offering Savings and Spending for one outgoing payment: switch source, retain requested value, show the appropriate fee, authorize once and verify recipient settlement and requester proof.
- **Why selected:** Remaining live Lightning variants: https://github.com/synonymdev/bitkit-ios/pull/1149#pullrequestreview-5681039586
- **Status:** Not run.

### MN-USDT-A — USDT mainnet

- **Scope:** Recurring · Android.
- **Steps and pass condition:** Complete a small production USDT send/receive. Use RS-SUB-A below for the outgoing payment, not an additional send. Verify recipient token balance, quoted/charged fee, final activity and balance after reopening.
- **Why selected:** Local-fork recovery already tested; production paymaster/provider settlement remains distinct. https://github.com/synonymdev/bitkit-android/pull/1681
- **Status:** Not run.

### MN-USDT-I — USDT mainnet

- **Scope:** Recurring · iOS.
- **Steps and pass condition:** Complete a small production USDT send/receive. Check recipient token balance independently, quoted/charged fee, final activity and balance after reopening. Combine physical payment authentication with RS-BIO-I.
- **Why selected:** Local controlled recovery acceptance is reusable. https://github.com/synonymdev/bitkit-ios/pull/1118
- **Status:** Not run.

### RS-SUB-A — Initial USDT subscription + PIN

- **Scope:** 3.1.0 · Android.
- **Steps and pass condition:** Use as MN-USDT-A's outgoing transfer. With payment PIN enabled: one Subscribe swipe → warning → correct PIN → one payment and Subscribed. Verify one recipient receipt/proof; no second payment swipe.
- **Why selected:** Existing automatic success had PIN disabled; PIN success covered manual retry. https://github.com/synonymdev/bitkit-android/pull/1568#pullrequestreview-5622474755
- **Status:** Not run.

### RS-BRIDGE — One production USDT bridge route

- **Scope:** 3.1.0 · choose one platform.
- **Steps and pass condition:** Use one currently enabled route as part of USDT funding/receive. Verify source settlement, destination credit, final bridge status and working transaction references. Record platform/network/provider. One route, not a provider/network matrix.
- **Why selected:** Changed bridge validation has fixture coverage; verify compatibility with the deployed provider. https://github.com/synonymdev/bitkit-ios/pull/1032
- **Status:** Not run.

### RS-BIO-I — Biometric lifecycle

- **Scope:** 3.1.0 · real iPhone.
- **Steps and pass condition:** Reopen locked app: one automatic prompt. Cancel/fail: usable PIN fallback, no prompt loop. Background/reopen: authentication works again. During a planned payment, cancel biometrics (no send), then explicitly authorize successfully.
- **Why selected:** Policy tests exist; physical-device evidence was not found. https://github.com/synonymdev/bitkit-ios/pull/788
- **Status:** Not run.

### RS-CAP-A — Receive above 10% channel capacity

- **Scope:** 3.1.0 · Android · REGTEST.
- **Steps and pass condition:** On a channel newly opened by this build, receive one Lightning payment above 10% of channel capacity with sufficient inbound liquidity. Independently verify settlement. Use regtest; do not open a mainnet channel for this check.
- **Why selected:** App journey unverified. Ordinary E2E receives 10,000 sats over a 100,000-sat channel (exactly 10%). https://github.com/synonymdev/bitkit-android/pull/1662#pullrequestreview-5615970105
- **Status:** Not run.

### RS-CAP-I — Receive above 10% channel capacity

- **Scope:** 3.1.0 · iOS · REGTEST.
- **Steps and pass condition:** On a channel newly opened by this build, receive one Lightning payment above 10% of channel capacity with sufficient inbound liquidity. Independently verify settlement. Use regtest; existing channels retain their old negotiated limit.
- **Why selected:** Upstream integration coverage does not execute the app journey. https://github.com/synonymdev/bitkit-ios/pull/1086#pullrequestreview-5615970107
- **Status:** Not run.

## What this example demonstrates

- Reuse the latest applicable evidence rather than copying an old regression checklist.
- Combine the Android subscription check with its USDT send, and iPhone biometric payment approval with an existing payment; assess the linked assertions independently.
- Use a controlled regtest channel for a release-specific boundary instead of creating an unnecessary mainnet channel.
- Keep accepted failures and incomplete device coverage visible without describing them as passed.
- Re-derive the next release's plan from its own diff, builds and evidence.
